Распределённая система преобразования доменных имён в IP-адреса и хранения другой информации о доменах.

Например:
```
google.com
    ↓
142.250.185.14
```

Благодаря DNS пользователю не нужно запоминать IP-адрес каждого сайта.

## Как работает DNS

Допустим, пользователь открывает:
```
google.com
```

**1. Клиент**

Компьютер проверяет локальные источники информации:
- `/etc/hosts`;
- DNS-кэш операционной системы;
- кэш браузера, если он используется.

Если адрес не найден, компьютер обращается к настроенному DNS-резолверу, например:

```
1.1.1.1
```

**2. DNS Resolver**

`DNS Resolver` - сервер, который выполняет поиск DNS-записей от имени клиента.

Сначала он проверяет собственный кэш. Если нужной записи нет, начинает поиск по иерархии DNS.

**3. Root DNS**

Корневой DNS-сервер не сообщает IP сайта, а указывает, где искать информацию о домене верхнего уровня:

```
.com
```

**4. TLD DNS**

Сервер домена верхнего уровня (`Top-Level Domain`) сообщает, какие DNS-серверы отвечают за:
```
google.com
```

**5. Authoritative DNS**

Авторитативный DNS-сервер хранит DNS-записи соответствующей зоны и возвращает запрошенную информацию.

Например:
```
google.com → 142.250.185.14
```

Резолвер передаёт ответ клиенту и сохраняет его в кэше.

Весь процесс:
```
             google.com
                 │
                 ▼
          Локальный кэш
                 │
             нет записи
                 ▼
          DNS Resolver
             1.1.1.1
                 │
             нет записи
                 ▼
             Root DNS
                 │
          Где искать .com?
                 ▼
             TLD .com
                 │
      Кто отвечает за google.com?
                 ▼
         Authoritative DNS
                 │
          142.250.185.14
                 │
                 ▼
          DNS Resolver
                 │
                 ▼
              Client
```

Важно: если запись уже находится в кэше резолвера, обращаться ко всей иерархии заново не нужно.

## Recursive и Iterative DNS

Существует два основных вида DNS-запросов.

**Recursive Query** - клиент просит DNS-сервер найти окончательный ответ.

```
Client:
Какой IP у google.com?

Resolver:
Сейчас найду.
```

**Iterative Query** - сервер возвращает известную информацию или указывает, к кому обратиться дальше.

```
Resolver → Root DNS

Root DNS:
Спроси серверы .com

Resolver → TLD .com

TLD:
Спроси авторитативный DNS google.com
```

Обычно клиент отправляет рекурсивный запрос резолверу, а резолвер выполняет итеративный поиск.

## UDP и TCP

Обычный DNS использует оба транспортных протокола на порту `53`.

|Протокол|Использование|
|---|---|
|[[UDP]] 53|Большинство обычных запросов и ответов|
|[[TCP]] 53|Крупные ответы, передача DNS-зон и другие случаи|

UDP используется часто, поскольку не требует предварительной установки соединения.

Если DNS-ответ слишком большой для передачи в одной UDP-датаграмме, сервер может вернуть усечённый ответ с флагом `TC`.

Клиент после этого может повторить запрос через TCP.

Исторически стандартный DNS ограничивал UDP-сообщения 512 байтами, но расширение `EDNS(0)` позволяет согласовывать больший размер.

Также существуют:

- `DoT` - DNS over TLS, обычно TCP 853.
- `DoH` - DNS over HTTPS, обычно HTTPS на порту 443.

Они позволяют шифровать DNS-запросы между клиентом и соответствующим DNS-сервером.

## Типы DNS-записей

|Тип|Назначение|Пример|
|---|---|---|
|**A**|Имя → [[IPv4]]|`site.com → 192.0.2.10`|
|**AAAA**|Имя → [[IPv6]]|`site.com → 2001:db8::10`|
|**CNAME**|Псевдоним другого имени|`www.site.com → site.com`|
|**MX**|Почтовые серверы домена|`site.com → mail.site.com`|
|**NS**|DNS-серверы зоны|`site.com → ns1.site.com`|
|**TXT**|Текстовая информация|SPF, DKIM, подтверждение домена|
|**PTR**|IP → имя (обратный DNS)|`8.8.8.8 → dns.google`|
|**SRV**|Адрес и порт сервиса|SIP, Kerberos|
|**CAA**|Какие CA могут выпускать сертификаты|Let's Encrypt, DigiCert|
|**SOA**|Служебная информация о зоне|Основной NS, серийный номер|

## DNS Cache и TTL

Чтобы не обращаться к DNS-серверам при каждом запросе, полученные записи временно сохраняются в кэше.

У каждой записи есть:
```
TTL — Time To Live
```

В DNS это время, в течение которого запись может храниться в кэше.

**Не путать с TTL IP-пакета**, который ограничивает количество переходов через маршрутизаторы.

Например:
```
site.com → 192.0.2.10

TTL = 300 секунд
```

Резолвер может использовать эту запись из кэша в течение пяти минут.

После истечения TTL ему потребуется снова получить актуальную запись.

Поэтому после изменения DNS-записей пользователи могут некоторое время получать старые адреса.

## DNS в Linux

Посмотреть, какие DNS-серверы настроены:
```
resolvectl status
```

Или:
```
cat /etc/resolv.conf
```

Запросить IPv4-адрес:
```
dig google.com A
```

Запросить IPv6-адрес:
```
dig google.com AAAA
```

Запросить записи определённого типа:
```
dig google.com MX
dig google.com NS
```

Обратный DNS:
```
dig -x 8.8.8.8
```

Отправить запрос конкретному DNS-серверу:
```
dig @1.1.1.1 google.com
```

Посмотреть полный путь поиска через DNS-иерархию:
```
dig +trace google.com
```

Последняя команда особенно полезна, чтобы на практике увидеть:
```
Root
 ↓
TLD
 ↓
Authoritative DNS
```

---

**Главная идея DNS:**

```
Доменное имя
     ↓
DNS Resolver
     ↓
DNS-запись
     ↓
IP-адрес
     ↓
Подключение к серверу
```

DNS не передаёт содержимое сайта — он помогает клиенту узнать, куда обращаться.
