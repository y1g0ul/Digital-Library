SSH (Secure Shell) - сетевой протокол для безопасного удалённого подключения к другому компьютеру. SSH работает поверх [[TCP]]. Стандартный [[ports]] `22`.

Через SSH можно:
- удалённо войти на сервер;
- выполнять команды;
- копировать файлы;
- делать туннели;
- использовать [[git]] по SSH;
- автоматизировать деплой.

## Как работает SSH

### Транспортный слой

**`Задача:`** Превратить обычное [[TCP]] соединение в шифрованное.
1. Клиент открывает [[TCP]] соединение на порт 22.
2. Обе стороны отправляют друг другу строку с названием и версией своей программы (открытым текстом).
3. Стороны обмениваются списками того, что каждая умеет:
	- Какими способами готова обмениваться ключами.
	-  Какими шифрами шифровать. 
	-  Чем проверять целостность.
	Из этих списков берется первый вариант который есть у обоих. 
4. Обе машины выполняют обмен ключами и получают общий секрет.
	Наружу уходят только публичные половины, а сам секрет ни разу не покидает машины. Из него обе стороны нарезают рабочие ключи. 
	- Отправка параметров: Стороны передают друг другу публичные математические параметры (или точки на эллиптической кривой).
	- Вычисление секрета: 
		- Клиент соединяет полученный публичный параметр сервера со своим тайным приватным параметром
		- Сервер делает наоборот -  соединяет публичный параметр клиента со своим приватным. 
	- Итог: Из-за особенностей математики обе машины получают абсолютно одинаковое число - общий секрет, на основе которого создаются ключи для шифрования всего дальнейшего сеанса. 

У каждого сервера есть постоянная пара ключей - ее называют хостовым ключом. Создается она один раз при установке. В конце обмена ключами сервер подписывает своим закрытым хостовым ключом отпечаток всего разговора который только что состоялся. Клиент провреяет эту подпись и если она сходится - свежий сессионный ключ намертво связан с личностью сервера. 

В отличии от браузера, гда за подтверждение подлинности ключа отвечают удостоверяющие центры, в [[linux/ssh|ssh]] идут на честный компромисс который называется доверием при первой встрече. При первом подлючении нам предлагают сверить короткий [[хеш]] открытого ключа сервера. Как только мы отвечаем `yes` ключ записывается в `~/.ssh/known_hosts` на машине. И дальше при каждом новом подключении клиент молча сверяет предьявленный ключ с сохраненным. 

### Слой аутентификации 

Он работает уже внутри зашифрованного соединения.  В нормальных системах аутентификация работает по ключу, а доступ по паролю закрыт. На сервере в файле `~/.ssh/authorized_keys` лежит ваш открытый ключ, который туда кладется один раз. При входе клиент берет блок данных, подписывает его закрытым ключом и отправляет только подпись. Сервер проверяет подпись открытым ключом из файла и если она сходится значит на том конце действительно есть закрытый ключ. 

Первым в подписываемый блок кладется идентификатор сессии, полученный из обмена ключами и уникален для этого соединения. Из-за этого подпись годится только один раз, для одной сессии. Если вы зашли на чужой сервер его владелец не сможет взять вашу подпись и предьявить ее другому серверу от вашего имени. 

### Слой соединения

Прошлый слой был просто шифрованной связью. Делает внутри этой связи несколько шифрованных каналов. У каждого канала есть собственный идентификатор и отдельный поток данных. Это называется **`мультиплексированием`**.

```text
Клиент
  │
  │ TCP :22
  ▼
Сервер
  │
  ▼
SSH Transport Layer
  │
  ├─ согласование алгоритмов
  ├─ обмен ключами
  ├─ получение общего секрета
  ├─ создание session keys
  └─ проверка host key сервера
  │
  ▼
Зашифрованный канал
  │
  ▼
SSH Authentication Layer
  │
  ├─ пароль
  └─ SSH-ключ
  │
  ▼
Пользователь подтверждён
  │
  ▼
SSH Connection Layer
  │
  ├─ Shell
  ├─ Exec
  ├─ SFTP
  ├─ Port Forwarding
  └─ другие каналы
```

Через SSH можно:

- копировать файлы;
- делать туннели;

## Как работает SSH

Работу SSH можно разделить на три этапа:
1. Создать защищённое соединение.
2. Проверить пользователя.
3. Создать внутри соединения каналы для терминала, передачи файлов и других задач.

---
### Транспортный слой

**`Задача:`** превратить обычное [[TCP]]-соединение в зашифрованное и убедиться, что клиент подключился именно к нужному серверу.

1. Клиент открывает TCP-соединение с сервером на порт `22`.
2. Клиент и сервер отправляют друг другу название и версию своей SSH-программы. Эта часть ещё передаётся открытым текстом.
3. После этого стороны обмениваются списками поддерживаемых алгоритмов:
    - как обмениваться ключами;
    - каким шифром шифровать данные;
    - как проверять целостность данных.
    Затем выбираются варианты, которые поддерживают обе стороны.
4. Клиент и сервер выполняют **обмен ключами**.
    Его смысл в том, что обе машины должны получить один и тот же секретный набор данных, но при этом **не передавать сам секрет по сети**.
    
    Упрощённо это работает так:
    - клиент создаёт свой приватный параметр и отправляет серверу только публичную часть;
    - сервер делает то же самое;
    - клиент объединяет публичные данные сервера со своими приватными;
    - сервер объединяет публичные данные клиента со своими приватными;
    - благодаря математике обе стороны получают одинаковый **общий секрет**.
    
    Сам общий секрет по сети никогда не передаётся.
    Из него клиент и сервер получают временные **сессионные ключи**, которыми затем шифруется текущее SSH-соединение.
    

```text
Клиент                         Сервер
   │                              │
   │──── публичные данные ───────►│
   │◄─── публичные данные ────────│
   │                              │
   ▼                              ▼
свой приватный                свой приватный
параметр                      параметр
   │                              │
   └──────────────┬───────────────┘
                  ▼
          одинаковый общий
                секрет
                  │
                  ▼
          сессионные ключи
```

#### Host key сервера

Мы создали зашифрованное соединение, но откуда клиент знает, что общается именно с нужным сервером, а не с кем-то, кто встал между ними?
Для этого у SSH-сервера есть постоянная пара ключей - **host key**.
Она создаётся на сервере и используется для подтверждения его личности.
В конце обмена ключами сервер подписывает данные текущего соединения своим закрытым host key.
Клиент проверяет эту подпись открытым host key сервера.

Таким образом клиент понимает:
> Сервер, с которым я сейчас создал зашифрованное соединение, действительно владеет этим host key.

Важно различать:
```text
Сессионные ключи
→ шифруют текущее соединение.

Host key
→ подтверждает личность сервера.
```

#### Доверие при первом подключении

В [[HTTPS]] подлинность сервера обычно подтверждают удостоверяющие центры.
В SSH чаще используется принцип **Trust On First Use** - «доверие при первом использовании». Когда мы впервые подключаемся к серверу, SSH показывает **fingerprint** его открытого host key.

Например:
```text
SHA256:xxxxxxxxxxxxxxxxxxxxxxxx
```

Fingerprint - это короткий [[хеш]] открытого ключа, который удобно сверить с настоящим владельцем сервера.

После ответа:
```text
yes
```

host key сервера сохраняется в:
```bash
~/.ssh/known_hosts
```

При следующих подключениях SSH автоматически сравнивает ключ сервера с сохранённым.

Если ключ неожиданно изменился, SSH предупреждает:
```text
REMOTE HOST IDENTIFICATION HAS CHANGED!
```

Это может означать, что:
- сервер переустановили;
- на сервере поменялись SSH-ключи;
- по этому IP теперь находится другой сервер;
- кто-то пытается подменить сервер.

---
### Слой аутентификации

**`Задача:`** проверить уже не сервер, а пользователя.

Этот этап происходит **внутри уже зашифрованного соединения**.
SSH поддерживает вход по паролю и по ключам. На серверах обычно предпочитают вход по SSH-ключам, а парольный вход часто отключают.

У пользователя есть:
```text
Private key
Public key
```

Приватный ключ хранится только на клиентской машине. Открытый ключ заранее кладётся на сервер в:
```bash
~/.ssh/authorized_keys
```

При входе клиент **не отправляет приватный ключ серверу**. Вместо этого он берёт данные текущего соединения и подписывает их приватным ключом. Сервер получает подпись и проверяет её открытым ключом из `authorized_keys`.

```text
Клиент
  │
  │ подписывает данные
  │ приватным ключом
  ▼
Подпись
  │
  ▼
Сервер
  │
  │ проверяет подпись
  │ открытым ключом
  ▼
Пользователь подтверждён
```

Если подпись правильная, сервер понимает:
> У клиента действительно есть соответствующий приватный ключ.

При этом сам приватный ключ ни разу не передаётся по сети.

В подписываемые данные входит идентификатор текущей SSH-сессии. Поэтому перехваченную подпись нельзя просто взять и использовать для входа на другой сервер или в другой SSH-сеанс.

---
### Слой соединения

**`Задача:`** использовать уже созданное защищённое соединение для реальной работы.

К этому моменту:
```text
TCP-соединение создано
        ↓
Шифрование настроено
        ↓
Сервер проверен
        ↓
Пользователь проверен
```

Теперь SSH может создавать внутри одного соединения несколько независимых **каналов**. У каждого канала есть свой идентификатор и собственный поток данных. Это называется **мультиплексированием**.

Например, через одно SSH-соединение могут работать:
```text
SSH Connection
│
├── Shell
│   интерактивный терминал
│
├── Exec
│   выполнение одной команды
│
├── SFTP
│   передача файлов
│
├── Port Forwarding
│   проброс TCP-соединений
│
└── другие каналы
```

То есть SSH - это не просто «удалённый терминал». Сначала он создаёт один защищённый канал между двумя машинами, а уже внутри него может передавать разные типы данных.
