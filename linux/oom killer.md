Механизм ядра [[Linux]], который принудительно завершает процессы, когда системе критически не хватает памяти и освободить её другими способами уже не получается.

Проще говоря:
```text
RAM закончилась
↓
Swap тоже закончился или не спасает
↓
ядру некуда выделять память
↓
Linux выбирает процесс
↓
процесс принудительно завершается
```

OOM Killer нужен для того, чтобы система не зависла полностью из-за нехватки памяти.

---

## Что происходит до OOM

Когда программе нужна память, ядро пытается её предоставить.

Сначала используется:
```text
RAM
```

Если RAM заканчивается, ядро может:
- освободить page cache;
- выгрузить часть памяти в [[swap]];
- попытаться reclaim-нуть неиспользуемые страницы;
- только после неудачи запустить OOM Killer.

То есть OOM Killer - это **крайняя мера**, а не первое действие при заполнении RAM.

---

## Почему вообще возникает OOM

Частые причины:
- [[процесс]] съел слишком много RAM;
- memory leak;
- слишком много процессов;
- маленький или отсутствующий swap;
- приложение получило слишком высокий лимит памяти;
- контейнер превысил свой memory limit.

Пример:
```text
RAM: 8 GB
Swap: 2 GB

Приложения используют:
10 GB

Новому процессу нужно ещё 1 GB
↓
памяти нет
↓
OOM
```

---

## Как ядро выбирает процесс

Linux не обязательно убивает процесс, который использует больше всего памяти.

Для каждого процесса вычисляется **OOM score**.

Посмотреть:
```bash
cat /proc/<PID>/oom_score
# текущая оценка процесса для OOM Killer

cat /proc/<PID>/oom_score_adj
# дополнительная настройка приоритета убийства
```

Чем выше `oom_score`, тем больше вероятность, что процесс будет выбран.

На оценку влияют:
- сколько памяти использует процесс;
- его настройки `oom_score_adj`;
- некоторые свойства процесса.

---

## oom_score_adj

Позволяет увеличить или уменьшить вероятность убийства процесса.

Диапазон:
```text
-1000 ... 1000
```

|Значение|Значение|
|---|---|
|`-1000`|практически запретить OOM Killer убивать процесс|
|`0`|обычный приоритет|
|`1000`|сделать процесс максимально вероятной целью|

Пример:
```bash
echo 500 > /proc/1234/oom_score_adj
# увеличить вероятность убийства процесса

echo -500 > /proc/1234/oom_score_adj
# уменьшить вероятность убийства
```

Значение `-1000` обычно требует root:
```bash
echo -1000 > /proc/1234/oom_score_adj
```

Использовать это нужно осторожно: если защитить слишком много процессов, ядру может оказаться нечего убивать.

---

## Как выглядит OOM

Часто приложение просто внезапно исчезает:
```text
Killed
```

Например:
```bash
./my-program
Killed
```

Но причина видна в логах ядра.

Проверить:
```bash
dmesg | grep -i oom
```

или:
```bash
journalctl -k | grep -i oom
```

Также полезно:
```bash
journalctl -k | grep -i "killed process"
```

Пример сообщения:
```text
Out of memory: Killed process 1234 (java) total-vm:...
```

Это означает, что ядро само завершило процесс из-за нехватки памяти.

---

## Global OOM и cgroup OOM

Есть два похожих случая.

### Global OOM

Вся система исчерпала память:
```text
Host
├── RAM закончилась
├── Swap закончился
└── OOM Killer
```

Ядро выбирает процесс во всей системе.

### cgroup OOM

Память в системе ещё есть, но конкретная [[cgroups]] достигла своего лимита. Это часто происходит в [[Docker]] и Kubernetes.

Например:
```text
Host RAM: 32 GB

Container limit: 512 MB
Container использует: 512 MB

↓
OOM внутри cgroup
```

При этом на сервере может оставаться ещё 20 GB свободной RAM.

---

## Docker и OOM

Например:
```bash
docker run --memory=512m nginx
```

Контейнеру разрешено использовать максимум 512 MB. Если процесс внутри превышает лимит, он может быть убит OOM Killer.

Проверить контейнер:
```bash
docker inspect <container>
```

Часто Docker показывает:
```text
OOMKilled: true
```

Это важный признак при диагностике внезапно завершившегося контейнера.

---

## systemd и OOM

[[systemd]] тоже может управлять памятью процессов через cgroups.

Например, для сервиса можно задать:
```ini
MemoryMax=1G
```

Тогда сервис и его дочерние процессы не смогут использовать больше 1 GB памяти.

Посмотреть ограничения:
```bash
systemctl show <service> | grep Memory
```

---

## OOM Killer и swap

Наличие [[swap]] может отсрочить OOM.

Без swap:
```text
RAM закончилась
↓
OOM наступает раньше
```

Со swap:
```text
RAM закончилась
↓
часть памяти выгружается в swap
↓
система продолжает работать
↓
если заканчивается и swap → OOM
```

Но swap не является заменой RAM. При активном swap система может стать очень медленной.

Проверить:
```bash
free -h
# посмотреть RAM и swap

swapon --show
# посмотреть активный swap
```

## Диагностика OOM

Если процесс неожиданно умер:
```bash
journalctl -k | grep -i oom
# проверить OOM события

journalctl -k | grep -i "killed process"
# посмотреть, какой процесс был убит

free -h
# посмотреть RAM и swap

ps aux --sort=-%mem | head
# процессы с наибольшим использованием памяти

top
# посмотреть использование памяти в реальном времени

cat /proc/<PID>/status
# подробная информация о памяти процесса
```

Для Docker:
```bash
docker inspect <container> | grep -i oom
# проверить, был ли контейнер убит OOM Killer
```

---

## Важные поля памяти процесса

В `/proc/<PID>/status` можно увидеть:

|Поле|Что показывает|
|---|---|
|`VmSize`|виртуальная память процесса|
|`VmRSS`|реально используемая RAM|
|`VmSwap`|сколько памяти процесса находится в swap|

```bash
grep -E 'VmSize|VmRSS|VmSwap' /proc/<PID>/status
```

При поиске процесса, который реально съедает RAM, особенно полезен `VmRSS`.

## OOM Killer и SIGKILL

Когда OOM Killer выбирает процесс, он обычно завершает его через `SIGKILL`.

Это означает:
```text
процесс не может перехватить сигнал
процесс не может корректно завершиться
процесс не успевает сохранить данные
```

Поэтому OOM может приводить к потере незаписанных данных приложения.

---

## Типичная ситуация

Сервер начинает тормозить:
```text
RAM почти 100%
Swap активно используется
Load Average растёт
процессы тормозят
```

После этого:
```text
java внезапно исчез
```

Проверяем:
```bash
journalctl -k | grep -i oom
```

Видим:
```text
Out of memory: Killed process 4215 (java)
```

Значит:
1. системе не хватило памяти;
2. ядро попыталось освободить память;
3. этого оказалось недостаточно;
4. OOM Killer выбрал `java`;
5. процесс был завершён.

После этого нужно искать **причину нехватки памяти**, а не просто запускать процесс заново.

---

## Главное для собеседования

**OOM Killer** - механизм ядра Linux, который запускается при критической нехватке памяти и выбирает процесс для принудительного завершения, чтобы освободить RAM и сохранить работоспособность системы.

Главная схема:
```text
Приложению нужна память
        ↓
RAM
        ↓
reclaim / page cache
        ↓
swap
        ↓
памяти всё равно нет
        ↓
OOM Killer
        ↓
oom_score
        ↓
SIGKILL процессу
```

Полезно помнить:
```text
OOM Killer ≠ просто "закончилась RAM"

Это последний этап после попыток ядра освободить память.
```

А в контейнерах возможен **cgroup OOM**, когда память закончилась только внутри лимита контейнера, хотя на самом хосте RAM ещё есть.
