## Чем git pull отличается от git fetch?

**Ответ:** 

`git fetch` только скачивает актуальную информацию из удалённого репозитория и обновляет локальное представление удалённых веток. При этом текущая локальная ветка сама по себе не изменяется.

`git pull` сначала получает изменения с удалённого репозитория, а затем сразу пытается объединить их с текущей локальной веткой. То есть git pull - это git fetch + последующее объединение изменений.


## Чем в Linux отличается soft link от hard link? Какое поведение будет при удалении файла оригинала? Можно ли создать hardlink на директорию?

**Ответ:** 

`Cимволическая ссылка` - это по сути ярлык, который хранит путь до другого файла или каталога. Путь может быть как абсолютным, так и относительным. Если удалить оригинальный файл, символическая ссылка останется, но станет битой и больше не сможет привести к файлу. Символические ссылки можно создавать на каталоги и на объекты, находящиеся в другой файловой системе.

`Жёсткая ссылка` - это ещё одно имя для того же inode и тех же данных. Поэтому нельзя в обычном смысле сказать, что один из файлов является оригиналом, а другой ссылкой - они равноправны. Если удалить одно имя файла, данные останутся на диске, пока существует хотя бы одна hard link на этот inode. Hard link нельзя создать между разными файловыми системами, потому что inode имеет смысл только внутри конкретной файловой системы. Обычно hard link на директории создавать нельзя. Это ограничение для того, чтобы не появлялись циклы в дереве каталогов и не ломалась структура файловой системы.

## Как проверить сетевую доступность между двумя Linux машинами?

**Ответ:** Можно проверить через ping. Маршрут до узла можно посмотреть через traceroute или mtr. Если нужно проверить конкретный TCP-порт, можно использовать nc. Для HTTP/HTTPS использовать curl.


## На каких компонентах Linux основана контейнеризация в Docker?

**Ответ:** На namespaces и cgroups.

`namespaces` отвечают за изоляцию: определяют, какие процессы, сеть, точки монтирования и другие ресурсы видит контейнер. `cgroups` отвечают за учёт и ограничение ресурсов, например CPU и памяти. Контейнер использует ядро хостовой Linux-системы, но процессы при этом изолированы.


## Почему вместо "COPY . ." / "RUN npm install" рекомендуют делать "COPY package.json" / "RUN npm install" / "COPY . ."?

**Ответ:** это связано с кешированием слоёв Docker.

Каждая инструкция в Dockerfile создаёт слой. Если сначала скопировать весь проект, то любое изменение в исходном коде изменит слой COPY. Из-за этого кеш для следующего шага станет неактуальным и npm install придётся выполнять заново.

Если сначала скопировать только package.json, установить зависимости, а уже потом копировать исходный код, то слой с зависимостями будет пересобираться только тогда, когда изменится package.json.

Изменение обычного исходного кода не заставит Docker заново устанавливать все зависимости.

## Могут ли два контейнера внутри одного Pod в Kubernetes слушать один и тот же порт?

**Ответ:** нет, если речь идёт об одном и том же IP-адресе и одном и том же протоколе.

Контейнеры внутри одного Pod используют общий network namespace, поэтому у них один IP-адрес и общее пространство сетевых портов. Например, если один контейнер уже слушает 0.0.0.0:8080, второй контейнер в этом же Pod не сможет занять этот же адрес и порт. При этом они могут слушать разные порты, например один 8080, а другой 9090.

## Какие виды JOIN знаете и чем они отличаются?

**Ответ:** 
- `INNER JOIN` возвращает только те строки, для которых нашлось совпадение в обеих таблицах.
- `LEFT JOIN` возвращает все строки из левой таблицы и подходящие строки из правой. Если совпадения нет, значения правой таблицы будут `NULL`.
- `RIGHT JOIN` работает наоборот: возвращает все строки из правой таблицы и совпадения из левой.
- `FULL JOIN` возвращает все строки из обеих таблиц: как совпавшие, так и те, для которых пары не нашлось.

## Что такое HAVING в SQL запросе? Чем отличается от WHERE?

**Ответ:** `WHERE` фильтрует отдельные строки до группировки. `HAVING` фильтрует уже сформированные группы после `GROUP BY`.
